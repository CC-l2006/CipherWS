### 2.2 设计要点（答辩可能会问）

**更换绑定邮箱是两步的**，这是本次改动最核心的安全设计：

```
① 验证当前邮箱  →  给「当前邮箱」发码，验过 → 服务端记 10 分钟标记
② 绑定新邮箱    →  给「新邮箱」发码，验过 → 检查标记 → 才允许改库
```

- 第 1 步的码发到**当前**邮箱，请求体不用传 email —— 服务端自己取库里的地址，防止被伪造
- 第 2 步必须有第 1 步的标记，否则报「请先验证当前邮箱（验证码 10 分钟内有效）」
  —— 这条**实测验证过**：跳过第 1 步直接换绑会被拒
- 标记只存内存（单实例够用），服务重启即失效，反而更安全

**验证码有 5 种用途，互不通用**：`register` / `reset` / `bind_old` / `bind_new` / `password`。
拿找回密码的码去注册、拿改密的码去验证旧邮箱，都会被「用途不匹配」拦下。

**修改密码需要**：原密码 + 新密码 + 确认 + 发到当前邮箱的验证码。
（保留了原密码字段是我的取舍 —— 你只要求加邮箱码，没说要删旧密码。若觉得多余，去掉 `PasswordReq.oldPassword` 与前端那个输入框即可。）

## 四、踩过的坑（别再踩）

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| 改错 env 文件 | 换了 SMTP 授权码还是 535 | 改 `deploy/mail.env.local`，**不是** `mail.env.example`；看文件修改时间就能判断改对没 |
| jar 被占用 | `mvn package` 报 `Unable to rename ...jar.original`，看着像编译错 | 先停服务再打包 |
| `git add -A` | 把磁盘上早已不存在的文件当成删除提交了 | 提交前先看 `git status` |
| 验证码 60 秒频控按邮箱算 | 刚换完邮箱马上改密，提示「发送过于频繁」 | 是刻意保留的（码按邮箱存储，不同用途会互相覆盖），等 60 秒即可 |
| 测试时验证码不回传 | 浏览器测试卡在「等验证码填入」 | 测试实例用 `--note.mail.enabled=false --note.auth.expose-code=true` 启动 |
| PowerShell 反引号 | 写 JS 模板字符串被吞、`$(if...)` 里带中文解析错 | 用单引号 here-string，或分步写 |
| nginx 1.24 | 写 `http2 on;` 直接报错 | 只能 `listen 443 ssl http2;` |
| 库名大小写 | Linux 上连接串写错库名 | 一律 `CipherWS` |
