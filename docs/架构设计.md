## 二、核心决策：后端要不要为子系统重写一个？

> **⚠️ 本节结论已作废（2026-10-05）**：后端最终选择 **微服务化**，见 [微服务架构.md](./微服务架构.md)。
> 下面的「不拆」分析保留作历史决策记录。

**结论（历史）：默认不拆，采用「模块化单体」。**

### 判断依据

| 子系统与主站的关系 | 决策 |
|---|---|
| 完全独立的数据，无共享 | 可拆，但**收益有限**（见下方成本） |
| 需要主站数据/用户/登录态 | **必须共用**，否则数据口径会分裂 |
| 暂不确定 | **先合后拆**，包结构隔离即可 |

### 为什么推荐不拆

1. **体量太小**：当前后端仅 7 个类、1 个接口（`GET /say/saying`），无数据库。拆分的运维成本会超过收益。
2. **内存翻倍**：单台 ECS 上两个 JVM，每进程通常 150–300MB 起。
3. **数据一致性风险**：拆分后若两边都写同一张表，会出现口径不一致——这类问题**排查成本极高**。

### 两种方案对比

**方案 A：模块化单体（推荐）**

```
server/
└── src/main/java/org/example/cipherwsserver/
    ├── common/          # 公共：Result 包装、异常处理、工具
    ├── config/          # WebConfig（CORS）、未来可加拦截器
    ├── modules/
    │   ├── say/         # 主站模块
    │   │   ├── controller/  service/  entity/
    │   └── design/      # 子系统模块
    │       ├── controller/  service/  entity/
    └── CipherWsServerApplication.java
```

- 部署：**一个 jar、一个进程、一个端口**
- 接口通过路径前缀自然隔离：`/say/**`、`/design/**`
- 将来要拆：把 `modules/design` 整体拷出去就是独立服务，成本可控

**方案 B：独立 Spring Boot 服务**

- 部署：两个 jar、两个进程、两个端口（各配 systemd）
- 适合：子系统技术栈不同、迭代节奏完全不同、需要独立扩缩容
- 代价：内存翻倍、两套日志、跨服务调用要处理超时与一致性

> **无论选哪个，只要共用数据库，就必须明确表的归属**：哪张表归谁写、谁只读。两个应用同时写同一张表是必须避免的。

## 三、多站点静态服务：三种实现方式

`server.js` 单站点，需要多入口时有三种做法：

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **多端口**（阶段一） | 起两个 `server.js` 实例，PORT/ROOT 用环境变量区分 | **零代码改动**，立刻能用 | 访问要带端口号 |
| **nginx 虚拟主机**（阶段二） | 按 `server_name` 分 root | 标准做法，可同域名 80/443 | 需装并维护 nginx |
| **改造 server.js 支持多站点** | 按 `Host` 头或配置映射到多个 root | 不装 nginx | 本质是在重新发明 nginx，不建议长期用 |

**当前采用「多端口」**，等域名就绪后切到 nginx。

## 四、本地笔记本的三种使用方式

| 方式 | 说明 | 风险 |
|---|---|---|
| **仅开发/构建**（推荐） | 本地写代码、`npm run dev` 预览、推 git，云端拉取构建 | 无 |
| 对外提供接入 | 本地起服务供公网访问 | **家庭宽带为动态 IP，且暴露内网入口有安全风险**；如需临时演示，用 `ssh -R` 反向隧道（只开隧道、不开放入站） |
| 作为备份构建机 | 本地产出 `dist/` 上传服务器 | 产物与服务器 Node 版本可能不一致 |

**结论：本地只做开发与构建，运行环境统一在云端**，避免"本地能跑、线上不行"的环境差异。

## 五、开发到部署流程

```
本地开发                     GitHub                    ECS
────────                    ───────                   ────
改代码                                               
  │                                                  
  ├─ npm run dev 本地预览（Vite :8000）               
  │                                                  
  └─ git push ─────────────▶ 仓库 ──── git pull ────▶ 
                                          │          
                                          ├─ npm run build
                                          └─ systemctl restart
```

约定：

- **前端构建必须在服务器上执行**，因为接口地址是**构建时注入**（`VITE_API_BASE_URL`）
- 改接口地址后**必须重新构建**，改服务器上的文件无效
- 后端为 jar 直跑，更新即替换 jar 并重启 systemd 服务
- 不要用 `rsync` 直接覆盖 `dist/`，容易留下旧版本的孤儿文件

## 七、端口规划

| 端口 | 用途 | 对外暴露 | 安全组放行 |
|---|---|---|---|
| 8000 | 主站前端（阶段一） | 是 | ✅ 已放行 |
| 3000 | 子系统前端（阶段一） | 是 | 需放行 |
| 8080 | 后端网关（Spring Cloud Gateway，沿用原后端端口） | 是 | 需放行（前端入口） |
| 8849 | Nacos 控制台（容器内 8080 映射到宿主 8849） | 建议否 | 仅内网 / 跳板机访问 |
| 8848 / 9848 | Nacos 主端口 / gRPC | 否 | 仅内网 |
| 8081 / 8082 | say / portal 微服务 | 否 | 仅内网 |
| 80 / 443 | nginx（阶段二） | 是 | 需放行 |

> **安全建议**：网关 8080 在接入 nginx 后应**停止直接对外暴露**，只留 `127.0.0.1` 供 nginx 反代，减少攻击面。

## 八、决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 子系统入口形式 | 子域名 `design.cipherws.icu` | 独立开发/部署；且 `createWebHistory()` 默认 base 为 `/`，放在子域根路径**无需改代码**（路径路由反而要改 base） |
| 后端是否拆分 | ~~暂用模块化单体~~ → **改为微服务**（2026-10-05） | 课程/答辩要求分布式架构：网关 + 服务 + Nacos + OpenFeign，见 [微服务架构.md](./微服务架构.md) |
| 静态服务 | 阶段一多端口，阶段二 nginx | 不阻塞当前开发，平滑过渡 |
| 本地笔记本角色 | 仅开发与构建 | 避免动态 IP 与内网暴露风险 |
