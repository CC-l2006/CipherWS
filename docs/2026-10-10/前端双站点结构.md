# 前端双站点结构（main + train）

> 落地日期：2026-10-10
> 背景：`train`（云间列车）原本是仓库根目录下的独立 Vite 工程，与主站平级、各自一套
> `node_modules`。为了按 **nginx 双 server 块**托管，把两个站点收进 `frontend/` 工作区。
> 域名备案已通过，两个站点都走 **80**。

## 一、目标结构

```
CipherWS/
├── frontend/                          # 前端工作区（不放业务代码）
│   ├── package.json                   # ★ 只做命令编排，无任何依赖
│   ├── server.js                      # 一份静态服务，--app 选择站点
│   ├── main/                          # 站点①：主站  → cipherws.icu
│   │   ├── src/  public/  index.html
│   │   ├── vite.config.js             # 别名 @ → src，dev 端口 8000
│   │   ├── package.json               # 依赖：vue-router / pinia / element-plus / sass …
│   │   ├── .env.development           # 不入库（.env* 已忽略）
│   │   ├── .env.production            # 不入库
│   │   ├── .env.example               # 入库模板
│   │   └── dist/                      # 构建产物，node server.js 的静态根
│   └── train/                         # 站点②：云间列车 → train.cipherws.icu
│       ├── src/
│       │   ├── components/            # ShaderCanvas / ControlPanel
│       │   ├── composables/           # useShaderRenderer.js
│       │   └── shaders/               # cloudtrain.frag / .vert（?raw 引入）
│       ├── index.html
│       ├── vite.config.js             # dev 端口 8001
│       ├── package.json               # name = cipherws-train
│       ├── probe.html                 # 调试页
│       ├── _ref/                      # 参考素材，已 gitignore（见第七节）
│       └── dist/                      # 构建产物，nginx 的 root
├── deploy/nginx/cipherws.conf         # ★ 双 server 块配置
├── server/                            # 后端微服务
└── docs/
```

**为什么两个子项目不合并成一个 Vite 工程**：主站是 `vue-router` history 模式的多页
SPA，要 SPA 回退；云间列车是单页 WebGL Demo，没有路由。两者的 `base`、回退策略、
依赖集都不同（主站 Vite 5、列车 Vite 6），合在一起只会互相牵制。
**也不使用 npm workspaces**：那会把依赖提升到根 `node_modules`，Vite 5 与 Vite 6
的具体版本、`sass` 的编译链都会互相污染。两个子项目各自 `npm install`，互不干扰。

## 二、命令速查（都在 `frontend/` 下执行）

| 命令 | 作用 |
| --- | --- |
| `npm run install:all` | 给 main 与 train 各装一次依赖 |
| `npm run dev:main` | 主站开发服 → `http://0.0.0.0:8000` |
| `npm run dev:train` | 列车开发服 → `http://0.0.0.0:8001` |
| `npm run build` | 依次构建两个站点（= `build:main` + `build:train`） |
| `npm run build:main` | 只构建主站 → `main/dist` |
| `npm run build:train` | 只构建列车 → `train/dist` |
| `npm run serve:main` | 用 `server.js` 起主站静态服务（:8000） |
| `npm run serve:train` | 用 `server.js` 起列车静态服务（:8001） |

> ⚠️ **不要在 `frontend/` 根目录执行 `npm install`**。根 `package.json` 不含依赖，
> 装了只会多出一个无意义的 `frontend/package-lock.json`。装依赖用 `install:all`。

## 三、server.js：一份脚本，两个站点

`server.js` 支持 `--app`（优先级高于 `APP` 环境变量），端口按站点取默认值：

| 站点 | 默认端口 | 静态根目录 |
| --- | --- | --- |
| `main` | 8000 | `frontend/main/dist` |
| `train` | 8001 | `frontend/train/dist` |

```bash
node server.js --app main              # 主站
node server.js --app train             # 云间列车
node server.js --app main --port 80    # 换端口
APP=train PORT=8001 node server.js     # 环境变量写法
```

新增第三个子站点只需两步：建 `frontend/<名字>/` 工程，在 `server.js` 的 `SITES`
注册表里加一行。

### 端口分配约定：8000 + 序号

`frontend/` 下的子项目按加入顺序顺延占用 `8000 + 序号`：

| 子项目 | 端口 | 位置 |
| --- | --- | --- |
| 主站 `main` | **8000** | `frontend/main/vite.config.js`、`server.js` 的 `SITES` |
| 云间列车 `train` | **8001** | `frontend/train/vite.config.js`、`server.js` 的 `SITES` |
| 下一个子项目 | 8002 | 依此类推 |
| 再下一个 | 8003 | 依此类推 |

选 8000 段而不是 3000 段，主要是避开常见占用：3000 被大量工具（Next.js、Grafana、
各种脚手架）默认使用，5173 是 Vite 默认，我们本机上就曾撞到一个跑在 5199 的别的项目。
8000 段整体留给我们自己，且要避开这几项已占用的：

| 端口 | 占用者 |
| --- | --- |
| 8080 | 后端网关 `cipherws-gateway` |
| 8081 / 8082 | `cipherws-say-service` / `cipherws-portal-service` |
| 8848 / 8849 | Nacos（容器内 8080 映射到宿主 8849） |

> ⚠️ **这些端口只用于本机预览与局域网访问，对外始终是 80/443 上的域名。**
> 用户访问的是 `cipherws.icu` 和 `train.cipherws.icu`，不是 `:8000` / `:8001`。
> 端口号只是「开发时怎么区分两个站」和「nginx 上游怎么找它们」，不是站点的公开身份 ——
> 所以新增子项目时**不需要**为它申请新的公网端口。

> 由于默认值就是 `main`，服务器上原有的 `cipherws-web.service`（`WorkingDirectory`
> 指向 `frontend/`、`ExecStart` 为 `node server.js`）**在迁移后无需修改就能继续工作**，
> 它会自动指向 `frontend/main/dist`。

## 四、nginx 双 server 块

配置文件：[deploy/nginx/cipherws.conf](../../deploy/nginx/cipherws.conf)
（部署到 `/etc/nginx/conf.d/cipherws.conf`）

| 站点 | 域名 | nginx 怎么处理 |
| --- | --- | --- |
| 主站 | `cipherws.icu`（含 `www`） | **反代**到 `127.0.0.1:8000`（node `server.js --app main`） |
| 云间列车 | `train.cipherws.icu` | **直托** `frontend/train/dist` |

主站 block 内还有两条后端反代：

| 路径 | 上游 | 说明 |
| --- | --- | --- |
| `/say/` | SakuraFrp 隧道 | 名言接口 |
| `/audio/` | SakuraFrp 隧道 | 音频流，`proxy_buffering off` 保证 Range 透传 |

### 主站为什么保留 node，不改成 nginx 直托

node 那份 `server.js` 已经实现了 SPA 回退（`/link` 刷新不 404）与文本资源 gzip，
继续由它处理能保证「本机预览」与「线上」行为完全一致，出问题只在一个地方排查。
代价是多一跳本机转发，性能损失可忽略。

将来若想省掉这个进程，把主站 block 的 `location /` 从 `proxy_pass` 改成
`root /opt/cipherws/frontend/main/dist;` + `try_files $uri $uri/ /index.html;` 即可，
产物不用重排。

### 列车站为什么不走 node

它是单页静态 Demo，没有路由也没有后端调用。nginx 直托**零额外部署步骤**，不用再起
第二个常驻进程。想改成走 node（`:8001`）的话，配置文件里已写好替换片段。

### 后端为什么也走 nginx

1. 后端跑在**本地笔记本**上，靠 SakuraFrp 内网穿透暴露。樱花节点对浏览器直连有
   安全认证限制（`http://` 访问直接返回 501），由服务器侧转发可以绕开这些**针对
   浏览器**的限制。
2. 直连是跨域，为此后端开了 `allowedOriginPatterns("*")` + `allowCredentials(true)`，
   这是实打实的安全问题。同源反代之后，这份宽松 CORS 配置可以直接删掉。
3. 后端真实地址不再出现在前端产物里，换隧道、换机器只改 nginx 一处。

若樱花隧道启用了**访问认证**，在 `/say/`、`/audio/` 两个 location 里补上凭据：

```nginx
proxy_set_header Authorization "Basic $(echo -n 'user:pass' | base64)";
```

配置文件里已经留了注释行，取消注释填进去即可。

### 上线步骤

```bash
# 1. 装 nginx
sudo apt update && sudo apt install -y nginx

# 2. 放入配置（仓库里已有）
sudo cp /opt/cipherws/deploy/nginx/cipherws.conf /etc/nginx/conf.d/cipherws.conf

# 3. 校验并加载（-t 失败时 nginx 不会加载新配置，线上不受影响）
sudo nginx -t && sudo systemctl reload nginx
```

安全组放行 **80**。

> ⚠️ **踩过的坑：安全组放行 ≠ 能访问。** 端口放行只是「允许流量到达主机」，
> 还得有进程真的在 80 上监听。我们一度只在阿里云控制台加了 HTTP(80) 规则，
> 但服务器上 nginx 根本没装，结果 `curl http://cipherws.icu/` 一直卡到超时。
>
> 判断方法是在服务器上直接看有没有人监听：
>
> ```bash
> sudo ss -tlnp | grep -w ':80' || echo "没有任何进程监听 80"
> nginx -v 2>&1 || echo "nginx 还没装"
> ```
>
> 另外注意一个容易误判的现象：这台机器上**没人监听的端口是「超时」而不是
> 「连接被拒绝」**（`nc -z` 探 9999、12345 也是超时）。所以「超时」这个现象
> 本身**不能**用来判断是不是被安全组拦了 —— 必须回到主机上看监听状态。
>
> 装完 nginx 后重跑 `./deploy/update-frontend.sh`，脚本会自动装配并校验配置。

验证：

```bash
curl -I  http://cipherws.icu/                    # 期望 200，主站 index.html
curl -s  http://cipherws.icu/say/saying?id=1     # 期望后端 JSON
curl -I  http://cipherws.icu/audio/stream?audio=HOYO-MiX%20-%20Da%20Capo.mp3
                                                 # 期望 200 + Content-Type: audio/mpeg
curl -I  http://train.cipherws.icu/              # 期望 200
```

**故障对照**：`/` 返回 502 说明 node（主站 systemd 服务，名字可能是 `cipherws-web`
或 `cipherws-web-main`）没起；`/say/` 与 `/audio/` 返回 502 说明笔记本上的后端或
樱花隧道掉线——此时静态页面照常打开，只是「每日一句」和音乐播放器取不到数据。

## 五、接口地址：直连 vs 同源

`VITE_API_BASE_URL` 是**构建时内联**的，改服务器上的文件无效，必须重新构建。

| 环境 | 文件 | 取值 | 请求实际发往 |
| --- | --- | --- | --- |
| 本地开发 | `main/.env.development` | `https://frp-hen.com:36691` | 浏览器直连隧道（本地没有 nginx） |
| 线上构建 | `main/.env.production` | **空** | 同源 `/say/...`、`/audio/...`，由 nginx 转发 |

留空时**必须保留 `=`**，写成 `VITE_API_BASE_URL=`。整行删掉的话
`import.meta.env.VITE_API_BASE_URL` 会变成 `undefined`，地址被拼成
`undefined/say/saying`。

### ⚠️ 踩过的坑：占位地址进了产物

`.env.example` 里原本最后一行是 `VITE_API_BASE_URL=https://your-backend-host:port`。
有人照文档 `cp .env.example .env.production` 之后忘了改，这个占位值就被构建时
内联进了产物，于是浏览器控制台刷屏：

```
获取数据失败 Failed to parse URL from https://your-backend-host:port/say/saying?id=2
```

**为什么难排查**：端口位置写的是字母 `port` 而不是数字，`new URL()` 直接抛
`Failed to parse URL` —— 请求**根本没发出去**，所以看 nginx 日志、看后端日志、
看跨域配置全都是干净的。而页面看起来也「正常」：每日一句显示的是组件里的兜底
文案（`今天是明天的昨天`），音乐播放器停在 `00:00/00:00`。很容易误判成鉴权或跨域。

**三个防线**（都已落地）：

1. `.env.example` 最后一行的默认值改成**空值**，`cp` 出来就是对的线上配置。
2. `update-frontend.sh` 检测到 `your-backend-host` 会**自动改写为空值**并说明原因；
   整行缺失时也会自动补上 `VITE_API_BASE_URL=`。
3. 脚本构建后会 grep 产物，发现残留占位地址立刻告警。

**症状对照表**：

| 控制台报错 | 原因 | 处理 |
| --- | --- | --- |
| `Failed to parse URL from https://your-backend-host:port/...` | `.env.production` 里是占位地址 | 改成 `VITE_API_BASE_URL=` 后重新构建 |
| 请求地址里出现 `undefined/say/saying` | `.env.production` 缺了 `VITE_API_BASE_URL` 整行 | 补上 `VITE_API_BASE_URL=` 后重新构建 |
| `CORS policy` / 被樱花拦截页 | `.env.production` 填了隧道完整地址（模式①） | 改成留空走同源反代 |
| 接口 502 | nginx 上游不通：后端或隧道掉线 | 检查笔记本上的后端与 SakuraFrp |

构建后自检：

```bash
grep -l 'frp-hen'      frontend/main/dist/assets/*.js   # 期望：无任何输出
grep -o '/say/saying'  frontend/main/dist/assets/*.js   # 期望：/say/saying（相对路径）
```

## 六、服务器端 systemd

主站需要 node 常驻（nginx 反代它）：

```ini
# /etc/systemd/system/cipherws-web-main.service
[Unit]
Description=CipherWS 主站静态服务
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/opt/cipherws/frontend
ExecStart=/usr/bin/node server.js --app main --port 8000
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

列车站由 nginx 直托，**不需要** unit 文件。若将来改成走 node，再照上面加一个
`--app train --port 8001` 的实例即可。

> **服务名叫 `cipherws-web` 还是 `cipherws-web-main` 都行 —— 脚本会自动认。**
> `update-frontend.sh` 的 `MAIN_SERVICE` 默认是 `auto`，会在 `systemctl` 里找
> `cipherws-web*` 单元，优先精确匹配 `cipherws-web-main`，其次 `cipherws-web`，
> 命中哪个就重启哪个，并把探测结果显示出来。所以**不需要为了跑脚本去改服务名**。
>
> 迁移前的 `cipherws-web.service` 服务的是已经不存在的 `frontend/dist`，但由于
> `server.js` 默认 `--app main`，它其实会自动指向 `frontend/main/dist` 继续正常跑。
> 想统一命名再换成上面那个 unit；不换也完全没问题。
>
> 要注意的是：**别让两个 unit 同时监听 8000**。如果新建了 `cipherws-web-main`
> 就先把旧的停掉：
> `sudo systemctl disable --now cipherws-web`

> 想写死服务名（比如单元名很特殊、探测不到）：
> `MAIN_SERVICE=我的单元名 ./deploy/update-frontend.sh`

## 八、服务器更新（一条命令）

仓库里提供了 `deploy/update-frontend.sh`，服务器上一条命令完成
「拉代码 → 补 `.env` → 按需装依赖 → 构建两个站点 → 重启服务 → 同步 nginx → 自检」：

```bash
cd /opt/cipherws
./deploy/update-frontend.sh
```

常用变体：

| 命令 | 场景 |
| --- | --- |
| `./deploy/update-frontend.sh` | 常规更新：拉取 + 构建两个站点 + 重启主站 |
| `--site main` / `--site train` | 只更新其中一个站点 |
| `--skip-pull` | 改了 `.env.production` 后重新构建（不拉代码） |
| `--ci` | 依赖有变动时用 `npm ci` 做可复现安装 |
| `--no-restart` | 只构建，不动服务与 nginx 配置 |

脚本的几个安全设计：

- **依赖只在必要时装**：对比 pull 前后两个提交，只有 `package.json` /
  `package-lock.json` 变了（或 `node_modules` 不存在）才会装依赖。
- **nginx 配置先备份、再校验、失败自动回滚**：绝不先覆盖再 `nginx -t`。一旦校验
  失败就把原文件还原（原本没有该文件就删掉），线上服务不受影响，也不会在
  `/etc/nginx/conf.d` 里留下一个坏配置害得下次 nginx 起不来。
- **脚本自更新会重跑**：如果这次 pull 里 `update-frontend.sh` 本身有更新，会用新
  版本重新执行一遍，避免「用旧逻辑跑新代码」。
- **`.env.production` 只补不覆盖**：文件不存在时按同源模式创建；存在但填了地址时
  只告警、绝不擅自改你的值。
- **服务名自动探测**：`MAIN_SERVICE` 默认 `auto`，在 `systemctl` 里找
  `cipherws-web*` 单元（优先 `cipherws-web-main`，其次 `cipherws-web`），
  所以服务叫哪个名字都能跑，不用为了脚本去改服务名。
- **失败即停**：任何一步失败都带明确提示退出，不会继续往下跑。

不加脚本时的等价手工命令：

```bash
cd /opt/cipherws
git pull

cd frontend
npm run install:all        # 仅 package.json 有变动时才需要
npm run build

sudo systemctl restart cipherws-web-main        # 主站（nginx 反代它）
sudo nginx -t && sudo systemctl reload nginx    # 改了 nginx 配置才需要

# 只更新其中一个站点：
#   npm run build:main   → 只重建主站
#   npm run build:train  → 只重建云间列车（纯静态，无需重启任何服务）
```
